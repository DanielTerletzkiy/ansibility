Reports templated values of role variables whose type is certainly outside the type the role's meta/argument_specs.yml documents (ANS-T020), for example

haproxy_settings_maximum_connections: 65535
haproxy_settings_kernel_somaxconn: '{{ haproxy_settings_maximum_connections }}'   # documented: str

Two types are compared with the documented one, and a value is reported only when both are outside it:

  • the logical type: what the author means. A bare {{ name }} has the type of every definition of name in the Ansible root (followed through further {{ name }} values, up to the root's type chain depth); a trailing filter gives its type (| int, | bool, | join, | length, | to_json …; | default(x) joins both); text around an expression always gives a string;
  • the runtime type: what the root's target ansible-core passes to the argument-spec validation. Up to 2.18, only a bare {{ name }} keeps a number or bool; every other template becomes a string unless it looks like a list, dict or bool. From 2.19 on, a single expression keeps its native value.

So '{{ port | int }}' for a str option is not reported for ansible-core 2.18 (it arrives as the string '8080'), while '{{ items | join(",") }}' for an int option is. A value is never reported when any definition on its chain is unknown (registered results, facts, loop variables, set_fact in free form), a vault secret, or null.

Values in role defaults and vars, group_vars/host_vars, hosts.yml, molecule inventories, play, block and task vars: and role parameters are checked against every role spec of the root that declares the variable, nested values included. The message names the definitions and says what ansible-core would do with the value. The quick fix appends | string (or | int, | float, | bool). The severity follows the root's Ansibility settings.
